# Архитектура и принятые решения

Документ объясняет, **почему** сделано именно так. Если решение кажется
странным — ответ, скорее всего, здесь.

## 1. Про «полную асинхронность»

Требование «чтобы работало асинхронно, мягко и без багов» на практике —
это две разные вещи, и путать их нельзя.

**Отзывчивость интерфейса.** Страница не перезагружается, действия
мгновенные, ничего не «прыгает». Решается HTMX и разметкой, а не `async def`.

**Фоновая обработка.** Уведомления, отчёты, экспорт, удаление по сроку
хранения. Решается Celery.

Поэтому в проекте:

- `async def` во вью **не используется вообще**;
- прод — Gunicorn с sync-воркерами (`config/wsgi.py`);
- `config/asgi.py` оставлен для совместимости, но не задействован.

Причина: Django ORM в асинхронных вью даёт `SynchronousOnlyOperation`,
утечки соединений и гонки, которые ловятся не на разработке, а в бою.
Выигрыш был бы только на длинных I/O-ожиданиях, которых здесь нет: журнал
и кабинеты — это короткие запросы к своей же базе. Вся «асинхронность»,
которую видит пользователь, живёт в HTMX-обновлениях без перезагрузки
страницы и в Celery-задачах.

Если понадобится долгий стрим (например, вебсокеты для живого журнала),
это делается отдельным ASGI-процессом рядом, а не переписыванием вью.

## 2. Мультиарендность

`Organization` — отдельная сущность, каждая доменная модель наследует
`TenantModel` с обязательным `organization`.

```
запрос → OrganizationMiddleware → contextvar → TenantManager.get_queryset()
```

- `objects` — фильтрует по текущей организации автоматически;
- `all_objects` — без фильтра, только админка, миграции, обслуживание;
- организация не определена → выборка **пустая**, а не полная.

Последнее — сознательный выбор: пустой список заметен и безопасен,
а утечка чужих данных незаметна и катастрофична. Для фоновых задач и
команд есть `organization_context(org)`, для админки — `unscoped()`.

Организация определяется по домену (`OrganizationDomain`), с запасным
вариантом `DEFAULT_ORGANIZATION_SLUG` для режима одного арендатора.
В тестах запасной вариант отключён — иначе он маскировал бы утечки.

Проверка: `tests/test_tenancy.py`.

## 3. Оценивание

Сервисный слой `apps/journal/services/grading.py`, во вью бизнес-логики нет.

- 100 баллов на модуль по каждому предмету, лимит хранится в `GradingScale`;
- структура по умолчанию: зачёт 25, две проверочные по 10, контрольная 15,
  40 баллов по занятиям с оцениванием (по 5 за занятие);
- сумма максимумов элементов модуля не может превысить лимит — ошибка
  сообщает, сколько распределено и сколько осталось;
- за поведение баллов нет: такого типа элемента не существует;
- баллы — `Decimal(5,2)`, никаких `float`;
- пересчёт итога — **явным вызовом сервиса**, не сигналом: сигналы трудно
  отлаживать, а порядок их выполнения неочевиден;
- пересчёт идёт в `transaction.atomic()` с `select_for_update()` на строке
  `ModuleResult` — два педагога не сломают сумму одновременной записью.

Пороги уровней противоречиво описаны в исходных материалах (60 — и незачёт,
и начало базового). Принято: `< 60` — незачёт, `60–69` базовый, `70–79`
повышенный, `80–100` продвинутый. Пороги лежат в БД и правятся владельцем.
Вопрос заказчику зафиксирован в `docs/STATUS.md`.

## 4. Права доступа

Два уровня:

1. **Роль** — `apps/accounts/permissions.py`, декоратор `role_required`.
2. **Объект** — `apps/journal/access.py`: педагог видит только свои занятия,
   родитель — только своих детей, ученик — только себя.

Вью не фильтруют вручную, а берут выборку из `access.py`. Одно место —
один набор правил, и его нельзя случайно обойти подстановкой id в URL.

Проверка: `tests/test_permissions.py`.

## 5. Персональные данные

- первичные ключи всех сущностей с ПДн — UUID: перебирать нечего;
- дата рождения и документы шифруются на уровне поля
  (`apps/core/fields.py`, Fernet, ключи из окружения);
  `django-cryptography` не используется — она не поддерживает Django 5;
- по зашифрованным полям нельзя фильтровать — поэтому шифруется только то,
  по чему не ищут;
- файлы с ПДн лежат вне `MEDIA_ROOT` (`PRIVATE_MEDIA_ROOT`) и отдаются
  вью с проверкой прав, а не напрямую через Nginx;
- мягкое удаление (`deleted_at`) для учеников, оценок, заявок, договоров:
  восстановление посреди учебного года возможно;
- `AuditLog` пишет просмотры карточек, изменения оценок, экспорт, входы
  и изменения прав — отдельно от доменных данных и с отдельной ротацией;
- в кабинетах нет сторонней аналитики: там персональные данные детей.

Проверка: `tests/test_privacy.py`.

## 6. Фронт

Дизайн токен-ориентированный: радиусы 0, границы 1px, размеры через
`clamp()`, адаптив на `flex-wrap` без медиа-запросов. Это точно ложится
на одну таблицу стилей с CSS-переменными и плохо — на утилитарные классы.

Поэтому вместо Tailwind — один файл `static/css/site.css` (~400 строк,
14 КБ) с теми же токенами, что в макете. Нет шага сборки, нет node_modules
на сервере, нет расхождения между макетом и продом. Если проект вырастет
до нескольких дизайнеров, Tailwind можно добавить поверх — токены уже есть.

Alpine.js не подключён: интерактив (шкала, сегменты, маска телефона,
cookie-баннер) — это ~150 строк обычного JS, из которых на первом экране
нужна только шкала.

Шрифты self-hosted и сабсеттированы под кириллицу: 120 КБ на все пять
начертаний, ни одного запроса к сторонним доменам (это ещё и требование
152-ФЗ — Google Fonts передаёт IP посетителя третьей стороне).

Устойчивость к обрыву связи (`static/js/journal.js`): введённый балл
живёт в `localStorage` до подтверждения сервера и уходит повторно, когда
сеть вернулась. Педагог не теряет введённое.

## 7. Что намеренно не сделано

- **Эквайринг.** Есть интерфейс `PaymentProvider` и `ManualProvider`
  (оплата по реквизитам, отметка администратором). Подключение эквайринга
  не потребует менять модель `Payment`.
- **Плагинная система оценивания.** Абстракция под то, чего ещё нет.
- **Публикация «настроения класса».** Идея, от которой отказались
  в обсуждении: агрегат состояния — внутренний инструмент.
- **Нейросетевые рекомендации.** Сначала журнал, который нужен с сентября.
